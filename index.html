01

Symmetric vs. asymmetric

Two keys, two jobs

Symmetric crypto is the workhorse. One key locks and the same key unlocks. AES and ChaCha20 push gigabytes per second, and every byte of your SSH session, keystrokes included, is encrypted this way. The catch is that both ends need the same key before they start, and the only channel they have is the one that's being watched. You can't mail the key to the server. The network is the mail.

Asymmetric crypto splits the key in two. A private key that never leaves its owner, and a public key you can hand to anyone, paste in a chat, or commit to a public repo. The two halves are linked by math: what one half does, only the other half can check or undo. Computing the private half from the public half is supposed to be infeasible, and chapters 2 and 3 are about why.

There are two ways to use a key pair. People mix them up constantly, including a lot of SSH tutorials.

Mode 1 · encryption

The padlock

You mail out open padlocks to anyone who asks. Anyone can put something in a box and snap your padlock shut. Only your key opens it.

public keylocks
private keyunlocks

Gets a secret to the key's owner.

Mode 2 · signatures

The signet ring

You press your ring into hot wax. Anyone holding a picture of your seal can check a stamp against it, but nobody can make a new stamp without the ring.

private keystamps (signs)
public keychecks (verifies)

Proves something came from the key's owner.

Gotcha

SSH login is the signet ring, never the padlock. The popular explanation goes "the server encrypts a random challenge with your public key and you prove yourself by decrypting it." That was SSH-1, from the 1990s. In SSH-2 (the only version OpenSSH has spoken since 2017), your client signs a blob that includes a fresh session ID, and the server checks that signature against the public key in authorized_keys. Nothing is ever encrypted with your SSH key. That's also why Ed25519, an algorithm that can only sign, works perfectly well as an SSH key.

So what does the encrypting? A symmetric key that both sides derive fresh for every connection through a key exchange (chapter 4). Your long-term key has exactly one job, which is proving identity. That gives SSH three separate jobs handled by three separate families of algorithms, and all three show up in the transcript above:

When someone asks what "encryption type" their SSH key uses, they're usually blending row one with row three. Your key type decides how you prove identity. It has nothing to do with how your traffic is encrypted.

02

RSA and the factoring problem

Trapdoors

A trapdoor function is easy to compute, hard to run backwards, and easy to run backwards again if you know one extra secret. All of classical public-key crypto is a search for good trapdoors, and RSA (Rivest, Shamir, Adleman, 1977) uses the oldest one: multiplying two primes is trivial, and splitting the product back into those primes is not.

You don't have to take that on faith. Race it:

At the slope you're seeing, trial division of a 2,048-bit RSA modulus would need about 21023 divisions. Real attackers use the General Number Field Sieve, which is enormously smarter, and it still costs about 2112 operations for RSA-2048 and 2128 for RSA-3072. That's what NIST means when it rates them at "112-bit" and "128-bit" security.

How RSA turns factoring into a key pair

The recipe is short. Pick two secret primes p and q and multiply them into the public modulus n. Compute φ(n) = (p−1)(q−1), which you can only do if you know the primes. Pick a public exponent e (almost always 65537), then solve for the private exponent d such that e·d ≡ 1 mod φ(n). Raising to the power e and raising to the power d undo each other mod n. The public key is (n, e). The private key is d, and anyone who can factor n can recompute it.

Here's the whole thing with numbers small enough to follow by hand. Sign a message as the key holder, then play verifier and try to tamper with it.

03

Elliptic curves, ECDSA and Ed25519

Curves

RSA keys are huge because factoring has clever shortcuts: the number field sieve is much faster than brute force, so n has to be enormous to stay ahead of it. Elliptic curves offer a trapdoor with no known shortcut of that kind. A 256-bit curve key buys the same ~128-bit security that RSA needs 3,072 bits for.

An elliptic curve is the set of points satisfying y² = x³ + ax + b. The strange, useful fact is that you can "add" two points on it and land on a third point on the same curve. The rule is geometric:

Lab · point-addition

Adding points on y² = x³ − x + 1

Draw a line through P and Q. It hits the curve at exactly one more point. Reflect that point across the x-axis and you have P + Q. To add a point to itself (P + P, "doubling"), use the tangent line at P instead.

Repeat the operation and you get scalar multiplication: k·G means G + G + … + G, k times. Computing it is fast even for astronomically large k, because you can double-and-add (2G, 4G, 8G… then sum the ones you need), which takes about 2·log₂(k) steps. Going backwards, from the point k·G to the number k, is the elliptic curve discrete logarithm problem, and it's the trapdoor.

Real curves don't use real numbers. They use integers mod a prime, which turns the smooth curve into a scatter of points with no visible pattern. That scatter is the point: consecutive multiples of G jump around unpredictably, so the public point gives you no hint about how many hops it took to get there.

Lab · discrete-log

The same idea over a finite field: y² = x³ − 3x + 6 (mod 101)

This curve has 109 points (108 dots plus the "point at infinity"), and 109 is prime, so any point generates all of them. The a = −3 is the same choice NIST made for P-256. Slide k to walk the multiples of G. Then hide a secret and brute-force it the way an attacker would have to.

No secret hidden yet.

With 109 points the attacker needs at most 108 tries. Curve25519's group has about 2252 points, and the best known attack (Pollard's rho) needs about 2126 steps. At a trillion steps per second that's roughly 200 million times the age of the universe.

Ed25519 vs. ECDSA: same kind of math, different engineering

Both are elliptic-curve signature schemes, and both give about 128-bit security at the 256-bit size. The differences are in which curve they use and how they sign.

  • The curves. Ed25519 runs on edwards25519, a twisted-Edwards form of Daniel J. Bernstein's Curve25519, over the prime 2255 − 19 (that's where the name comes from). Every constant has a published justification. ECDSA in SSH uses NIST's P-256, P-384 and P-521, standardized around 2000 and generated from seed values nobody has ever explained. There's no known weakness in the NIST curves, but the unexplained seeds are why some people prefer to avoid them.
  • The nonce. Every ECDSA signature needs a fresh, secret, perfectly random number. Reuse one even once, or let the random numbers be slightly biased, and the private key falls out of the signatures with high-school algebra. Sony's PS3 signing key was extracted in 2010 because Sony used the same nonce every time. In 2024, PuTTY versions 0.68 through 0.80 were found to generate biased nonces for P-521 keys, and about 60 signatures were enough to recover the private key (CVE-2024-31497). Many of those signatures were sitting in public Git commit histories.
  • Ed25519 designs the problem out. It derives each signature's nonce by hashing the private key together with the message. Same message, same nonce, no random number generator involved at signing time, so there's nothing to get wrong.
04

Diffie–Hellman, X25519, ML-KEM

Agreeing on a secret

Back to the problem from chapter 1. Your laptop and srv01 need a shared symmetric key, and every byte between them is visible to Eve. In 1976 Whitfield Diffie and Martin Hellman published a way for two parties to build a shared secret in public. The classic explanation uses paint, and it holds up.

Lab · paint-exchange

Diffie–Hellman with paint

Everyone agrees on a common paint in public. Alice and Bob each pick a secret colour and mix it with the common paint in equal parts, then swap the mixtures in public. Each adds their own secret to what they received. Both end up with the same colour. Eve saw every public mixture, but paint can't be un-mixed, and her best attempt comes out wrong.

With numbers, the "paint" is exponentiation mod a prime. Everyone knows a prime p and a generator g. Alice picks a secret a and publishes A = ga mod p. Bob picks b and publishes B = gb mod p. Alice computes Ba, Bob computes Ab, and both get gab mod p. Eve has g, p, A and B and needs a discrete logarithm to get any further.

Lab · dh-numbers

Diffie–Hellman mod p

X25519: the same trick on a curve

Swap "g to the power a" for "a times the point G" and you have elliptic-curve Diffie–Hellman. X25519 is ECDH on Curve25519, where each side's public value is 32 bytes. As curve25519-sha256 it was OpenSSH's default key exchange from 2014 until the post-quantum hybrids took over.

Forward secrecy, or why a stolen laptop doesn't unlock old sessions

SSH generates a brand-new ephemeral key pair for every connection (and every re-key), uses it for one exchange, and wipes it. Your id_ed25519 plays no part in producing the session key; it only signs. So if someone steals your laptop next year along with a packet capture of today's session, the capture stays sealed. The numbers that could have opened it no longer exist anywhere. They can impersonate you from then on, which is why you revoke a stolen key, but they can't read the past.

ML-KEM: a lockbox instead of paint

The post-quantum half of today's default works differently. ML-KEM (FIPS 203, formerly Kyber) is a key encapsulation mechanism. The client sends a public "lockbox" (an encapsulation key). The server puts a fresh random secret inside, snaps it shut, and sends back the ciphertext. Only the client can open it. That's the padlock from chapter 1, and it shows up here for a one-time ephemeral key, never for your identity key. The trapdoor is a lattice problem called module learning-with-errors, which nobody knows how to solve efficiently with or without a quantum computer.

OpenSSH doesn't bet on ML-KEM alone. mlkem768x25519-sha256 runs X25519 and ML-KEM-768 in the same round trip and hashes both secrets together, K = SHA-256(K_mlkem ‖ K_x25519). Eve has to break both. The cost is bandwidth: the client's share grows from 32 bytes to 1,216 (1,184 for ML-KEM plus 32 for X25519) and the server's reply from 32 to 1,120. It's specified in RFC 10042, published in 2026.

          Inside the files

          Here's what lives in ~/.ssh and what each file is for. The permissions matter: with StrictModes yes (the default), sshd ignores authorized_keys if your home directory, ~/.ssh or the file itself is writable by anyone else, and ssh refuses to use a private key that other users can read.

└── config               -rw-r--r-- 644  per-host settings (IdentityFile, ProxyJump…)

          A public key, decoded

          A .pub line has three space-separated parts: the key type, a base64 blob, and a comment. The comment is a label for humans and ssh ignores it. The blob is a sequence of length-prefixed fields: a 4-byte big-endian length, then that many bytes, repeated. Paste any public key below, including a line straight out of authorized_keys or known_hosts.

          Fingerprints and the first-connection prompt

          A fingerprint is the SHA-256 of the decoded key blob, printed as base64 without padding. It's what ssh shows you the first time you meet a host, and it's the thing you're supposed to check before typing yes. Get the real value over a path you trust, like the server's console or your config management:

          # on srv01's console (or via IPMI / iDRAC / the hypervisor console)
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
# 256 SHA256:WzVuwy8D+WXGTOcCPZdomeXlotiyg8aoZc6QlyD3aYQ root@srv01 (ED25519)

# show randomart next to the fingerprint on every connection
ssh -o VisualHostKey=yes srv01
          Gotcha

          ssh-keyscan srv01 | ssh-keygen -lf - is handy for populating known_hosts, but it fetches the key over the same network you don't trust yet. It tells you what the server says its key is, which is exactly what a man-in-the-middle would also say. Use it for convenience, not verification.

          The private key file

          Modern OpenSSH writes private keys in its own openssh-key-v1 format. This is the actual structure of a passphrase-protected Ed25519 key generated with ssh-keygen -t ed25519 -a 100: 290 bytes once the base64 armor is removed.

          -----BEGIN OPENSSH PRIVATE KEY-----PEM-style armor around base64.
          "openssh-key-v1\0"Magic string. Older tools wrote PEM/PKCS#1 (BEGIN RSA PRIVATE KEY) instead.
          ciphername: aes256-ctrCipher protecting the private section. none if you skipped the passphrase.
          kdfname: bcryptTurns your passphrase into that AES key. Deliberately slow.
          kdfoptions: salt (16 B), rounds = 100The -a 100 lands here. The default is 16. More rounds make every guess against a stolen file slower, and your own unlock slightly slower.
          number of keys: 1Always 1 in practice.
          public key (51 B)The same blob as the .pub file, stored unencrypted, so tools can identify the key without asking for the passphrase.
          encrypted private section (160 B)Everything below is ciphertext until the passphrase is supplied.
          checkint, checkintThe same random 32-bit number twice. If they match after decryption, the passphrase was right.
          key type, public keyssh-ed25519 and the 32-byte public key again.
          private key (64 B)For Ed25519: the 32-byte secret seed followed by the 32-byte public key.
          comment, padding 1 2 3…The comment lives in the encrypted part. Padding brings it to the cipher's block size.

          No passphrase means ciphername none: anyone who can read the file is you. Add or change a passphrase in place with ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519.

          authorized_keys can do more than allow

          Each line in authorized_keys can start with options that fence in what that key is allowed to do. This is how you give a backup job a key without giving it a shell.

          restrict,from="192.0.2.20",command="/usr/local/bin/backup-receive" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… backup@srv01
          • restrict turns off PTY allocation, port, agent and X11 forwarding in one word (OpenSSH 7.2+). Add back only what you need, e.g. restrict,pty.
          • from="…" only accepts the key from matching source addresses or hostnames.
          • command="…" forces that command no matter what the client asks to run. The requested command is still available to it in $SSH_ORIGINAL_COMMAND.
          • expiry-time="20271231" stops accepting the key after a date. verify-required demands a PIN or biometric on security-key logins.

          ssh-agent: the key stays put, the signatures travel

          The agent holds decrypted private keys in memory and signs on request over a Unix socket ($SSH_AUTH_SOCK). ssh never touches the key itself; in step 9 of the handshake it just asks the agent to sign. That design is why agent forwarding is dangerous: ForwardAgent yes exposes that socket on the remote host, and anyone with root there can ask your agent to sign logins to anywhere your key works, for as long as you're connected. They never get the key. They don't need it.

          # hop through a bastion without exposing your agent to it
ssh -J bastion.example.net srv01

# load a key with a lifetime, and ask for confirmation on every use
ssh-add -t 8h -c ~/.ssh/id_ed25519

# OpenSSH 8.9+: only allow this key to be used to reach srv01, even through forwarding
ssh-add -h srv01 ~/.ssh/id_ed25519

          Every key type, KEX and cipher in OpenSSH

          Field guide to algorithms

          First, key type vs. signature algorithm

          A key type is what's in the file. A signature algorithm is how that key signs. For most types they're the same name, but RSA is the famous exception. One RSA key (type ssh-rsa) can sign three ways: ssh-rsa (with SHA-1), rsa-sha2-256 and rsa-sha2-512. OpenSSH 8.8 (September 2021) disabled the SHA-1 flavour by default after researchers showed chosen-prefix SHA-1 collisions cost under US$50K. Your 2016 RSA key still works fine; it just signs with SHA-512 now. What breaks is talking to ancient devices that only understand the SHA-1 flavour, and the fix belongs in a per-host block, never a global one:

          # ~/.ssh/config: re-enable SHA-1 RSA signatures for ONE legacy box
Host old-switch
    HostKeyAlgorithms +ssh-rsa
    PubkeyAcceptedAlgorithms +ssh-rsa

          Terrapin, briefly

          CVE-2023-48795 let an attacker in the path quietly delete a message at the very start of encryption, affecting chacha20-poly1305 and CBC with EtM MACs. The practical impact was small (it could strip some keystroke-timing protections), and OpenSSH 9.6 fixed it with "strict KEX", which both sides must support. ssh-audit tells you if a server is still exposed.

          How we got here

          1. 1995SSH-1. Tatu Ylönen writes it after a password-sniffing attack on his university's network.
          2. 1999OpenSSH forks from the last freely licensed SSH release, as part of OpenBSD 2.6.
          3. 2006SSH-2 standardized as RFCs 4251–4254. DSA is the only mandatory signature algorithm, because the alternatives were patent-encumbered at the time.
          4. 2011ECDSA keys and ECDH key exchange arrive (OpenSSH 5.7).
          5. 2014Ed25519 keys and curve25519-sha256 (6.5). Curve25519 becomes the default key exchange.
          6. 2015DSA disabled by default (7.0).
          7. 2017SSH-1 removed entirely (7.6).
          8. 2019Default RSA size → 3072 (8.0), following NIST SP 800-57.
          9. 2020FIDO security keys: ecdsa-sk and ed25519-sk (8.2).
          10. 2021SHA-1 RSA signatures off by default (8.8).
          11. 2022Post-quantum by default: sntrup761x25519 hybrid key exchange (9.0).
          12. 2023Ed25519 becomes ssh-keygen's default (9.5). Terrapin disclosed; strict KEX ships (9.6).
          13. 2024mlkem768x25519-sha256 added (9.9), built on the brand-new FIPS 203.
          14. 2025DSA deleted; ML-KEM hybrid becomes default (10.0, April). The client starts warning on non-post-quantum key exchange; XMSS removed (10.1, October).
          15. 2026RFC 10042 standardizes the ML-KEM hybrids. Experimental ML-DSA-44 + Ed25519 signatures in 10.4 (July). OpenSSH 10.5 (11 August) is the current release as of this page.

          Shor, Grover, harvest-now-decrypt-later

          The quantum problem

          Two quantum algorithms matter here, and they hit very differently.

          • Shor's algorithm (1994) factors integers and computes discrete logarithms in polynomial time on a large enough quantum computer. That takes out RSA, finite-field DH, ECDH, ECDSA and Ed25519: every public-key algorithm in this page that doesn't start with "ML-". Bigger keys don't meaningfully help; RSA-4096 falls to the same attack as RSA-2048.
          • Grover's algorithm (1996) gives a square-root speedup on brute-force search. It roughly halves the effective strength of symmetric keys, so AES-256 and ChaCha20's 256-bit key drop to about 128 bits. That's still fine. Your session ciphers don't need to change.

          Why key exchange went first

          An attacker doesn't need a quantum computer today to benefit from one later. They can record your encrypted SSH sessions now, store them, and decrypt them once the hardware exists. That's "store now, decrypt later" (also called harvest now, decrypt later), and it means any session protected by a classical key exchange is only as private as the time until a cryptographically relevant quantum computer shows up.

          Signatures don't have that problem. A signature only has to hold up at the moment you log in; forging one in 2035 doesn't let anyone into a session from 2026. The deadline for signatures is "retire classical keys before the quantum computer exists," not "now." That's why OpenSSH made post-quantum key exchange the default in 2022 and only shipped experimental post-quantum signatures in 2026.

          Since 10.1, the client says so when a connection falls back to a classical exchange:

          ** WARNING: connection is not using a post-quantum key exchange algorithm.
** This session may be vulnerable to "store now, decrypt later" attacks.
** The server may need to be upgraded. See https://openssh.com/pq.html

          Whether that matters for a given connection comes down to a comparison usually credited to Michele Mosca: if the time your data must stay secret (X) plus the time it takes you to migrate (Y) is longer than the time until a quantum computer can break your crypto (Z), you're already exposed.

          Lab · mosca

          Is recorded traffic from today at risk?

          Nobody knows Z. OpenSSH summarizes current estimates as 5 to 20 years, with many observers expecting the mid-2030s. NIST's draft transition plan (IR 8547) deprecates RSA and elliptic-curve algorithms after 2030 and disallows them after 2035.

          Why hybrids, instead of just switching

          The post-quantum algorithms are young. In 2022, SIKE, which had made it to the fourth round of NIST's own competition, was broken with a classical attack that ran in about an hour on a single laptop core. Combining ML-KEM with X25519 means the worst case, if ML-KEM falls the same way, is exactly the X25519 security everyone had the day before. The composite signatures follow the same logic.

          The standards, as of September 2026

          • FIPS 203, ML-KEM (key encapsulation, was Kyber). Final, August 2024. This is what's in your key exchange.
          • FIPS 204, ML-DSA (signatures, was Dilithium). Final, August 2024. The PQ half of OpenSSH's experimental composite key.
          • FIPS 205, SLH-DSA (hash-based signatures, was SPHINCS+). Final, August 2024. Conservative math, very large signatures (7.8 KB and up).
          • FIPS 206, FN-DSA (was Falcon). Still a draft; final publication expected late 2026 or early 2027. Compact signatures, hard to implement safely.

          Harden the server side

          A drop-in file keeps your changes separate from the distro's sshd_config. On OpenSSH 10.x the default key exchange list is already right, so this mostly shuts doors rather than picking algorithms.

          /etc/ssh/sshd_config.d/10-hardening.conf
          PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin prohibit-password
AuthenticationMethods publickey
PubkeyAcceptedAlgorithms ssh-ed25519,sk-ssh-ed25519@openssh.com,ssh-ed25519-cert-v01@openssh.com,rsa-sha2-512,rsa-sha2-256
# OpenSSH 9.1+: refuse small RSA keys

# Optional: make post-quantum KEX mandatory (9.9+ server). Clients older than 9.0 will fail to connect.
# KexAlgorithms mlkem768x25519-sha256,sntrup761x25519-sha512,sntrup761x25519-sha512@openssh.com
          # validate before reloading: a typo'd algorithm name stops sshd from starting
sudo sshd -t && sudo systemctl reload ssh     # "sshd" on RHEL-family

# confirm what's actually in effect
sudo sshd -T | grep -Ei '^(passwordauth|kexalgorithms|pubkeyaccepted|requiredrsa)'

# audit from the outside (github.com/jtesta/ssh-audit)
pipx install ssh-audit && ssh-audit srv01
          Gotcha

          Every algorithm name in KexAlgorithms or PubkeyAcceptedAlgorithms has to exist in that server's OpenSSH, or sshd refuses to start. mlkem768x25519-sha256 needs 9.9+, the bare sntrup761x25519-sha512 spelling needs 9.9+, and Ubuntu 24.04 ships 9.6. Run ssh -Q kex on the box and sshd -t before you reload, and keep a second session open while you test.

for f in ~/.ssh/*.pub; do ssh-keygen -lf "$f"; done

          Field note · Junos

          Junos takes Ed25519 directly: set system login user alice authentication ssh-ed25519 "ssh-ed25519 AAAA… alice@laptop-202609". Junos also accepts ssh-ecdsa and ssh-rsa, and in FIPS mode Ed25519 is refused. Network OSes tend to trail OpenSSH on key exchange, so expect the post-quantum warning when you manage switches and routers. Silence it per host with WarnWeakCrypto no-pq-kex rather than globally, so you still notice when a server regresses.
